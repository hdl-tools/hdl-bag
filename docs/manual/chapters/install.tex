\chapter{Installing}
\label{ch:install}

BAG needs Python 3.11 or newer. It runs on Linux, macOS and Windows. Reading, checking
and generating need nothing else. Lint, simulation and formal need the EDA tools of
section~\ref{sec:eda}, and on macOS they run in the container image of
section~\ref{sec:eda} rather than natively.

BAG is on PyPI. Install it from there, or from its repository or a checkout, in a
virtual environment.

\section{Installing BAG}

\begin{enumerate}
\item Create and enter a virtual environment: \cmd{python -m venv .venv}, then
  activate it as your shell requires.
\item Install BAG: \cmd{pip install hdl-bag}\\
  or, for the unreleased main branch,
  \cmd{pip install git+https://github.com/hdl-tools/hdl-bag.git}\\
  or, from a checkout, go to the folder that holds \file{pyproject.toml} and run
  \cmd{pip install .}
\item For \cmd{bag sim}, add the \code{sim} extra, which installs cocotb and
  cocotbext-axi at the versions the generated tests are written for:
  \cmd{pip install "hdl-bag[sim]"}, or
  \cmd{pip install "hdl-bag[sim] @ git+https://github.com/hdl-tools/hdl-bag.git"},
  or \cmd{pip install ".[sim]"} from a checkout.
\end{enumerate}

\section{The EDA tools}
\label{sec:eda}

\begin{description}
\item[Lint and compile] slang, Verilator and Verible. \cmd{bag lint} runs the tools
  named in Project > \setting{Lint tools}; Verilator also builds the simulation model.
\item[Simulation] Verilator, with cocotb from the \code{sim} extra.
\item[Formal] SymbiYosys and Yosys with the yosys-slang plugin, from the OSS CAD Suite.
\end{description}

BAG is tested with one version of each tool, listed in the file \file{tools.lock} of
the repository:

\begin{center}
\begin{tabular}{ll}
\toprule
Tool & Version \\
\midrule
Verilator & v5.052 \\
slang & v12.0 \\
Verible & v0.0-4296-g0f262651 \\
OSS CAD Suite (SymbiYosys, Yosys) & build of 2026-10-02 (SymbiYosys v0.69) \\
\bottomrule
\end{tabular}
\end{center}

BAG also works with other versions of the tools, but they are not tested:

\begin{itemize}
\item \cmd{bag formal} adds a note to its report, for example
  \code{note: sby 0.70 is not the pinned v0.69}.
\item \cmd{bag lint} treats a built-in waiver that waives nothing as an error
  (\ruleid{WAIVER-UNUSED}) only with the pinned version of the tool; with another
  version it is a note. Another version can also report findings the pinned one does
  not.
\end{itemize}

The simplest way to get every tool at its pinned version is the container image
\code{ghcr.io/hdl-tools/hdl-bag-tools:main}, built from \file{tools/Dockerfile} in the
repository. It holds the tools, Python and BAG's dependencies, but not BAG itself:
mount your checkout and install BAG in it. The image is published for
\code{linux/amd64} and \code{linux/arm64}, so the same tag runs natively on an
x86-64 Linux machine and on an Apple Silicon Mac.

If you installed BAG from PyPI and have no checkout, use the image tagged with your
release: \texttt{ghcr.io/hdl-tools/hdl-bag-tools:v\bagversion} for this one. Each release
tags the image its tools were validated with. The image does not hold BAG, so
\cmd{uv tool run} installs the same version from PyPI inside the container, with the
\code{sim} extra that \cmd{bag sim} needs, and a named volume keeps uv's cache between
runs. Run this from the directory that holds \file{out/}, after \cmd{bag generate} has
written it there; replace \cmd{bag lint out/} with any other \cmd{bag} command that needs
the tools:

\lstinputlisting{examples/files/docker-pypi.sh}

For another release, change both versions in it, the image tag and the one after
\code{==}, to that release. Only the current directory is visible in the container: a
spec or output directory elsewhere needs its own mount. The container runs as root, so on
a Linux host the files it writes under \file{out/} belong to root; take them back with
\cmd{sudo chown -R "$USER" out/} before you write \file{out/} again on the host.

\subsection{Installing the tools on a host}
\label{sec:install-tools}

\file{scripts/install_tools.py} installs the same pinned tools outside a container, for
\code{linux-x64}, \code{linux-arm64} and \code{darwin-arm64}. It reads
\file{tools.lock}, checks every archive against \file{tools/tools.sha256} before
unpacking it, and prints the \code{PATH} to set.

Run it with \cmd{uv run --no-project python scripts/install_tools.py}: with
\cmd{--list} it resolves and prints what it would install without touching the network,
with no options it installs, and with \cmd{--check} it reports each installed tool
against the lock. \cmd{--prefix} chooses where, defaulting to
\path{/opt/hdl-bag-tools}.

It never runs \cmd{sudo} or a package manager: where it needs a writable prefix or a
build dependency it prints the command to run and stops.

\section{macOS}
\label{sec:macos}

Reading a workbook, \cmd{bag check}, \cmd{bag ir}, \cmd{bag generate} and the
collateral are supported on macOS on Apple Silicon and need nothing but Python.

The EDA flows run in the container image, which is native on Apple Silicon. Run
\cmd{docker run} on \code{ghcr.io/hdl-tools/hdl-bag-tools:main} with your checkout
bind-mounted at \path{/work}, and give the container its own virtual environment through a
named volume and \code{UV\_PROJECT\_ENVIRONMENT}, so it does not share the host's
\path{.venv}. \code{UV\_LINK\_MODE=copy} avoids hard links across the mount.

Run this from your checkout, after \cmd{bag generate} has written \file{out/}. It lints
the design with the pinned tools. Replace \cmd{uv run bag lint out/} with any other
\cmd{bag} command that needs the tools:

\lstinputlisting{examples/files/docker-lint.sh}

Only the checkout is visible in the container. A spec or an output directory outside it
needs its own mount, for example \code{-v /data/specs:/specs}, and you then name it
by its path in the container, \path{/specs}.

The reason the flows are not run natively is Verilator. It publishes no macOS binary and
cannot be built from source at the pinned version on macOS~27: the system
\cmd{flex} emits a \code{yy\_create\_buffer} that does not match Verilator's
\file{src/V3PreLex.h}, and Homebrew's \cmd{flex} emits a scanner using
\code{yy\_hold\_ptr} that \file{verilog.l} does not declare. Upstream fixed building
against the newer \cmd{flex} after the pinned release.
\file{scripts/install_tools.py} refuses that build with this explanation rather than
failing part-way through it.

A Docker credential helper on macOS may not be on the default \code{PATH}; if
\cmd{docker} reports \code{docker-credential-desktop: executable file not found}, add
\path{/Applications/Docker.app/Contents/Resources/bin} to \code{PATH}.
